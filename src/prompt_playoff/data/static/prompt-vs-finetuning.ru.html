Когда файн-тюнить модель — а когда промпта достаточно

Практическое, опирающееся на исследования руководство по выбору между промпт-инжинирингом, few-shot in-context learning, RAG, файн-тюнингом, дистилляцией и инструментами/агентами — по качеству, стоимости, задержке и стабильности в продакшене.

Файн-тюнинг нужен не тогда, когда вы просто хотите «сделать модель умнее». Он оправдан, когда замеры показывают, что нужное поведение не удаётся получить надёжно, дёшево или достаточно быстро с помощью промптинга, примеров в контексте, поиска релевантных фактов или более способной базовой модели.

1. Начните с типа задачи

Промптинг, поиск, файн-тюнинг и вызов инструментов решают разные задачи. Большие языковые модели часто способны адаптироваться к задаче по инструкциям и демонстрациям без обновления весов — поэтому промптинг и in-context learning следует рассматривать как настоящие механизмы адаптации, а не просто как слой интерфейса. [1]

ЗадачаЛучший первый подход
Модель не понимает, чего именно вы хотитеПромпт-инжиниринг
Нужно показать желаемое поведение примерамиFew-shot / ICL
Модели не хватает релевантных фактов или документовRAG
Информация часто меняетсяПоиск / RAG / инструменты
Модель должна вызывать API, базы данных, CRM или программыИнструменты / агент
Задача понятна, но нужное поведение остаётся нестабильнымФайн-тюнинг
Большой повторяющийся промпт определяет стоимость выводаФайн-тюнинг / дистилляция
Меньшей модели нужно специализироваться на узкой повторяющейся задачеФайн-тюнинг
Исследования instruction tuning показывают, что обучение с учителем на парах «инструкция–ответ» может существенно изменить, насколько надёжно модель следует инструкциям и обобщает на новые задачи. [2] Недавний обзор характеризует instruction tuning как механизм повышения управляемости модели и её соответствия задаче. [7]

Предположим, у вас уже есть сильный промпт:

85% → 93% → 93.5% → 93.6%
Вы выходите на плато качества промпта.
Остаточные ошибки систематичны
Теперь файн-тюнинг — серьёзный кандидат.
1000 eval cases

best prompt
accuracy = 91%

errors:

- special company rule: 2%
- unusual wording: 2%

Важное слово — систематичны. Один плохой ответ — не доказательство того, что нужно менять веса. Стабильный паттерн ошибок, измеренный на репрезентативном наборе после итераций промпта, — гораздо более сильное доказательство.

3. Когда промптинга обычно достаточно

Возьмём стандартную задачу извлечения:

«Extract the customer name, order ID,
and issue from this email. Return JSON.»

Способная языковая модель уже обладает общими навыками понимания текста и извлечения. Few-shot промптинг позволяет ей вывести структуру задачи из демонстраций без обновления весов. [1]

Extract:
- customer_name
- order_id
- issue

Return valid JSON using this schema...
Правило: если способность уже существует, сначала попробуйте раскрыть и ограничить её через инструкции, схемы вывода, примеры и оценку.

4. Сильный аргумент за файн-тюнинг

Допустим, у компании 73 внутренние категории поддержки, границы которых зависят от правил организации:

"refund pending" → PAY_REFUND_PENDING

if refund initiated less than 3 days ago →
PAY_REFUND_PROCESSING

but if merchant disputed →
MERCHANT_DISPUTE_REFUND

except enterprise users →
ENT_REFUND_ESCALATION

Если у вас также есть 20 000 корректно размеченных исторических тикетов, то это классическая задача адаптации с учителем: стабильное распределение входов, стабильная таксономия целей и много примеров желаемого поведения. Исследования instruction tuning показывают, что обучающие примеры могут научить модель конвенциям ответа и следованию задаче. [2] [4]

Before fine-tuning:

1500-token prompt
+
ticket
+
output


After fine-tuning:

ticket
→
PAY_REFUND_PENDING

Выгода не только в качестве. Успешно дообученная модель может сократить повторяющиеся токены промпта, уменьшить задержку, повысить стабильность и позволить развернуть меньшую модель.

5. Не путайте нехватку знаний с ошибкой поведения

100,000 pages
product documentation
internal policies
prices
contracts
FAQ

Файн-тюнинг обычно не первый механизм, когда главное требование — доступ к большому меняющемуся массиву фактов. Retrieval-Augmented Generation был создан именно для того, чтобы объединить параметрические знания модели с внешней непараметрической памятью, решая задачи провенанса и обновления мировых знаний. [3]

User
 ↓
Retrieval
 ↓
relevant documents
 ↓
LLM
 ↓
answer + citations
Знания → контекст.
Поведение → веса.

Но доменный файн-тюнинг всё равно может помочь

Файн-тюнинг может адаптировать терминологию, конвенции ответа, границы классификации и специализированное поведение. Результаты LIMA — полезное напоминание: относительно небольшое число тщательно отобранных примеров может научить модель сильному поведению ответа, даже когда большая часть фактических знаний приходит из предобучения. [4]

             DOMAIN BEHAVIOR
                    ↓
              Fine-tuned LLM
                    ↑
                    │
User → Retrieval → Context

Поэтому RAG и файн-тюнинг дополняют друг друга: поиск даёт актуальные знания, а настройка формирует то, как модель ведёт себя с этими знаниями.

6. Пять сильных сигналов, что файн-тюнинг оправдан

1. У вас много примеров «это правильно»

INPUT → CORRECT OUTPUT
INPUT → CORRECT OUTPUT
INPUT → CORRECT OUTPUT
...

Это особенно привлекательно, когда целевое поведение проще показать, чем описать длинным списком правил. Исследования вроде LIMA показывают, что тщательно подобранные обучающие примеры могут существенно управлять поведением модели. [4]

2. Промпт превратился в монстра

SYSTEM PROMPT
14,000 tokens

RULES
75 rules

EXAMPLES
42 examples

Long-context ICL может оставаться эффективным даже с сотнями или тысячами демонстраций, но эти демонстрации должны обрабатываться при каждом выводе. Это создаёт реальный компромисс между адаптацией через контекст и адаптацией через веса. [5]

3. Нужна очень высокая стабильность

классификациямаршрутизацияструктурированное извлечение нормализациятаксономия модерациидетекция интентаNER

Часто это узкие задачи с измеримыми метками и понятными ошибками — именно та среда, где адаптацию с учителем можно объективно оценить.

4. Маленькая спец. модель должна заменить большую общую

70B general model
+
large prompt
+
20 examples

↓ SFT / distillation

7B specialist model

Эксперименты EMNLP 2025 на восьми задачах классификации показали, что специализированным меньшим моделям часто хватало небольшого числа размеченных примеров — в среднем около 100 в тестовых условиях — чтобы догнать или превзойти большие общие модели. Точная точка безубыточности сильно зависела от задачи. [6]

5. Есть постоянная остаточная ошибка

Base model
     ↓
prompt
     ↓
few-shot
     ↓
RAG if necessary
     ↓
eval

После нескольких итераций:

6.3% failure

Если эти ошибки кластеризуются вокруг стабильного поведения, которое модель раз за разом не может выполнить, превратите случаи ошибок и их исправленные ответы в кандидаты на обучающие данные.

7. Когда файн-тюнинг, скорее всего, неверный ход

  • Промпт выдал один плохой ответ.
  • Главное — свежие или часто меняющиеся факты.
  • Есть лишь горстка слабых или противоречивых примеров.
  • Определение задачи меняется каждую неделю.
  • Сама таксономия ещё нестабильна.
  • Нет репрезентативного набора для оценки.
  • Нельзя описать режимы ошибок, которые должен исправить тюнинг.
  • Базовая модель фундаментально не обладает нужной способностью.
incapable base model
+
500 examples
≠
frontier reasoning model
Файн-тюнинг сильнее всего как специализация. Не стоит относиться к нему как к волшебному способу создать произвольные новые способности из неподходящей базовой модели.

8. Модели с длинным контекстом сдвинули границу

Старая эвристика «мало примеров — промптинг; много примеров — файн-тюнинг» больше недостаточна. Эксперименты NAACL 2025 показали, что long-context ICL может продолжать улучшаться с тысячами демонстраций на некоторых задачах. То же исследование обнаружило, что файн-тюнинг был более требователен к данным в тестовых условиях, но мог превзойти long-context ICL при дополнительном обучении. [5]

Today you should consider all of these:

quality
inference cost
training cost
latency
context size
dataset quality
task stability
traffic volume
maintenance burden

Это делает решение экономическим, а не только статистическим: одно и то же целевое качество может иметь очень разные операционные затраты в зависимости от того, живёт ли адаптация в промпте или в весах.

             RAG                     Fine-tuning

Few-shot ICL может адаптировать поведение модели без обновления весов. [1] Instruction tuning меняет поведение на уровне весов. [2] RAG добавляет внешние знания. [3] Архитектура должна соответствовать типу ошибки.

Вторая продакшен-ветка: экономика

quality is already acceptable
but
cost / latency is not
        ↓
fine-tune or distill a smaller model

Файн-тюнинг может быть оправдан, даже когда промптинг уже достигает целевого качества: целью оптимизации может быть экономика вывода, а не чистая точность.

10. Критерий решения

Прирост качества + Экономия на выводе + Выигрыш в задержке
>
Стоимость обучения + Стоимость данных + Стоимость поддержки

Задача также должна быть достаточно стабильной, чтобы освоенная специализация оставалась полезной достаточно долго, чтобы окупить затраты на создание данных, обучение, оценку и поддержку.

Полезный вопрос не «Можно ли это решить промптом?»
А «Может ли промптинг достичь нужного качества, стоимости и задержки SLO на реальном распределении данных?»
Если узкое место в…Использовать
Спецификация задачиПромпт
Не хватает демонстрацийFew-shot / ICL
Не хватает или устарели знанияRAG / Поиск
Внешние действияИнструменты / Агент
Стабильное поведение под задачуФайн-тюнинг
Высокая стоимость или задержка выводаФайн-тюнинг / Дистилляция
Промптинг говорит модели, что делать в этом контексте.
RAG говорит ей, что нужно знать в этом контексте.
Файн-тюнинг меняет то, что она склонна делать по умолчанию.

Для маленьких локальных моделей специализация может стать привлекательной довольно рано. Недавние контролируемые эксперименты показывают, что небольшие дообученные модели могут догнать или превзойти большие модели общего назначения на узких задачах классификации с удивительно скромным объёмом размеченных данных, хотя точка безубыточности сильно зависит от задачи. [6]
