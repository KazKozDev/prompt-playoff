Measure prompts, don’t guess

Most prompt engineering is still done by intuition. Prompt Playoff turns that into an experiment — getting as much useful performance as possible out of the model you already have before reaching for a larger model, a more expensive API, or fine-tuning.

Give it a real task, examples with known answers, a model, and a prompt. It runs the prompt across the dataset, grades every answer, measures quality and reliability, checks whether the difference is meaningful, and records exactly what was tested.

That makes prompt optimization a model-efficiency problem as much as a prompt-writing problem. If a smaller or local model can reach the required quality through the right prompt, examples, structure, and search strategy, there may be no reason to pay for a larger one.

The goal is not to find a universally “best” prompting technique. There is no best technique in the abstract. There is only the best technique for a particular task, model, and dataset — and that has to be measured.

It is an exam for a prompt

Take a pile of tasks whose correct answers are known. Run your prompt on a live model across all of them. Compare what the model said against the expected answer, count the hits, and out comes a number.

The point is to replace:

“I think the prompt is better this way.”

with:

“0.83 against 0.71 on two hundred examples.”

That is the basic unit of the application: a measured result attached to a specific prompt, model, dataset, and run configuration. A score without those things is not portable evidence.

Why this matters

  • A technique that sounds sophisticated can make a task worse.
  • A longer prompt can reduce quality.
  • A reasoning stage can help arithmetic and hurt extraction.
  • A prompt that wins on one model may lose on another.
  • A benchmark result can disappear when you move from a toy dataset to your own production-like examples.

Prompt Playoff is built around that fact. It does not assume that a published prompting method is good; it asks the method to prove itself on your task.

What we have already measured

The application ships with completed benchmark reports under docs/benchmarks/. The results are a useful demonstration of why measurement matters.

Thirteen literature methods on few-nerd

Eleven of twelve alternatives lost to the plain baseline prompt. The ranking tracked token spend almost exactly in the wrong direction: the more a method forced the model to reason, restate, or decompose, the worse it performed on entity extraction.

That task is mostly reading, not reasoning. An intermediate restatement can pull the model away from the exact surface form it is supposed to extract.

Built-in optimization vs MIPROv2

On entity-extraction-hard, with the same split for both methods:

MethodQuality GainNotes
native greedy search+0.000Changed the prompt repeatedly and found nothing better
DSPy MIPROv2+0.090Searched instructions and examples together; used ~half the calls

A large cloud model behaved the same way

On a separate reading task, adding a reasoning stage resulted in:

  • Quality: -0.028
  • Tokens: 2.9×
  • Latency: 4.4×

On arithmetic, both approaches hit the 1.000 ceiling, where no difference could show. That is why the application contains a catalogue of techniques rather than a ranking: the winner depends on the task.

The three parts of an exam

1. The examples

These are the tasks and their correct answers. One task per row. They decide what the number is actually about. If the examples do not resemble the work you care about, a good score does not mean much.

2. The graders

Graders are small deterministic checks that compare the model answer with the expected answer and return a score from 0 to 1. Different tasks need different graders: arithmetic, extraction, classification, translation, and open-ended prose cannot be evaluated the same way.

3. The run

The run records the evaluation model, model settings, number of runs per example, prompt fingerprint, dataset, graders, latency, and token usage. The model is part of the measurement: change the model and you have changed the exam.

How imported data stays honest

  • Gold text is sliced from the source sentence: If the source says “Captain Orin”, the expected entity is taken from that exact surface form. The model does not lose points because somebody normalized the gold answer differently.
  • Unrequested entity types become empty examples: If a sentence contains only a film title but the schema asks for people and places, the correct answer is empty, not a model error.
  • Empty examples are preserved: Negative cases matter. If every row contains something to extract, an aggressive guessing model looks excellent because false positives are under-tested.
  • Corpus limitations are recorded: If a source corpus has a known annotation quirk, the preset documents it rather than hiding it.

How an answer gets checked

Graders fall into two families. The distinction matters because one family contributes primarily to quality, while the other is used to compute reliability.

Meaning graders: is the answer right?

field_f1Partial credit over extracted fields or entities. Primary extraction score.
token_f1Word overlap against one reference answer. A similarity, not a correctness score — read the section below before acting on it.
exact_matchCharacter-for-character equality.
label_accuracyCorrect class label for classification tasks.
numeric_closeNumeric value matches within allowed tolerance.
unit_testsGenerated code is executed against tests in a sandbox.
grounding_overlapHow much answer wording is supported by supplied sources.
contains_allEvery required fact is present in the output.
coverageRecall only: how much target information was found.
schema_shapeRequired structural keys are present.
regex_matchOutput follows the required regular expression pattern.
injection_resistancePrompt injection failed to expose the canary secret.
agreementMultiple generated answers agree with one another.

Contract graders: is the answer shaped correctly?

json_validityOutput parses as valid JSON.
json_schemaOutput fully matches the provided schema.
no_proseNo unwanted conversational chatter around the answer.
allowed_labelsLabel comes strictly from the allowed set.
forbidden_contentThe answer contains none of the words or patterns the task rules out.
length_limitOutput stays within the character/word limit.
omission_checkOutput is not obviously truncated or bloated against input.
deduplicationLists contain no duplicate entries.
glossary_consistencyRequired translations follow the binding glossary.
tool_successTool calls executed without returning errors.
python_syntaxGenerated Python parses without syntax errors.

Graders are deterministic by default. The same answer always receives the same score. They cost nothing to run, take milliseconds, and you can inspect the exact rule.

Open-ended prose: the number that looks like a verdict and is not

Bring a drafting task — a reply, a summary, a marketing email — and every row carries one reference answer: the reply somebody actually sent. Nothing can compare an answer to that character for character, so the run falls back to token_f1, which counts the words the two share.

A correct answer worded differently scores like a failure. Two replies can say the same thing and share a fifth of their words. 0.1 to 0.3 is the ordinary range for a good answer against one human reference, and 1.0 is not reachable by anything short of a copy. Read token_f1 as drift between two runs of the same prompt, never as a share of answers that were right — that reading has sent more than one person off to fix a prompt that was working.

So the report does not leave you to know that. Beside a word-overlap headline it prints the chance level: what the same metric already scores when the answer was written for a different row of the same set. It is measured off the rows, costs no model call, and settles the question the warning only describes.

prompt-playoff list-datasets prints it for every bundled set, and it is on the shelf and on the dataset you upload. On the bundled marketing-email corpus it is 0.41: an answer written for a different row already scores 0.41, so almost none of the score is about the prompt. A set like that cannot be scored by word overlap at all.

The bundled support-reply corpus was the extreme case — every reference in it is a template, so its floor was 0.63 — and it is no longer scored this way. It now carries the requirement the work actually has: the reply must carry the order reference back. Every drafting set in the catalogue that could be given such requirements has been.

What to score open-ended work on instead

Give the rows requirements a rule can decide. None of them needs a reference answer, which is the point — they are enforceable exactly where a reference answer does not exist.

contains_allThe facts that have to survive: the order number, the date, the amount.
forbidden_contentWhat the draft may never say: a refund nobody authorised, a competitor, a leftover [INSERT NAME].
length_limitThe length the channel allows.
regex_matchThe shape the answer has to take — a subject line, a signature, a reference code.
grounding_overlapHow much of the answer came from the evidence rather than from the model.
glossary_consistencyTerms rendered the way the glossary binds them.

The bundled translation and summarization sets are written this way, which is why neither is scored by word overlap even though both answer in prose.

And that is what CI gates

A committed check bounds one named grader with grade.<grader>_min, so a requirement nobody has a reference answer for still fails the build:

require:
  grade.contains_all_min: 1.0        # every reply cites the order number
  grade.forbidden_content_min: 1.0   # none of them promises a refund
  grade.length_limit_min: 0.98       # they fit the channel

A plain quality_min over a word-overlap headline is refused rather than enforced: it would commit CI to how closely answers echo one person's wording, which a better prompt can lose and a worse one can keep. grade.token_f1_min is allowed and means what it says — watch this metric for drift — and writing it out is how you record that you know the difference.

You do not have to write those requirements by hand

In the app it is one button: open Datasets, pick the shape of the work beside your set — answers to somebody, summaries of a source, drafts — and press Add requirements. From the terminal, prompt-playoff annotate-dataset rows.jsonl --contract reply --in-place. Either way it derives them per row: the identifier the reply has to carry back, the unfilled [INSERT NAME] that must not ship, the length the channel allows. A check is kept only where that row's own reference answer already meets it, so nothing it writes can mark a model wrong for answering as well as a person did. --contract summary requires the facts the human summary kept; --contract draft does the format checks alone.

Run it with no --contract and it writes down the graders the tool would otherwise have guessed — so the choice on record is yours rather than the tool's. Every run also reports which of its graders nobody chose.

When a rule genuinely cannot decide it

Tone, persuasiveness, whether an explanation lands: for those, use Evaluation → Answer judging. The judge is shown two answers with the order hidden, and must be a different model from the one being evaluated.

It is no longer one pair at a time. Judge a whole run on that screen judges every row of a recorded run against the reference answer that row already carries and reports the share of rows your prompt won — a win rate against the person who wrote those references, where 0.5 means it writes about as well as they did.

A judged number stays a model's opinion. One review item for the batch under Production → Reviews, and no route into a scorecard or a committed threshold. A bar defended by a model's mood on the day is not a bar; what CI enforces is what a rule decided.

And the prompt search refuses the same number

A search maximises whatever number it is handed. Handed word overlap on rows whose answers already resemble each other, it reliably raises it — by drifting towards the wording every row shares — which makes the prompt worse while the score goes up. So the search stops before its first model call when the floor is at or above 0.35, and says what to give the rows instead. One button gets past it, and relabels what comes back: Search anyway, and read it as drift (--allow-noisy-objective on the CLI).

The two headline numbers

quality — meaning and correctness

quality is chosen from the task's meaning graders using a fixed preference order (e.g. unit_tests for code, field_f1 for extraction, label_accuracy for classification, numeric_close for arithmetic, and token_f1 only when nothing better applies to prose). The selected grader is marked as the headline metric in the run, and where its number cannot mean what it looks like, the warning is printed beside it.

reliability — structural contract and stability

reliability combines compliance with contract graders and stability across repeated runs. A system can therefore be accurate but structurally unreliable, structurally clean but semantically wrong, or good on average but unstable. One number would hide those differences; two numbers expose them.

Five rules without which the number means nothing

1. Use at least one hundred examples. On six examples, a 5% change can mean one row flipped. On tiny datasets, apparent improvements are often noise. Evaluation → Results → Significance exists to test that.

2. Run each example more than once. Three runs per example is the default rule. With one pass, stability is 1.000 by definition because there is nothing to compare against — that is not evidence of stability.

3. Keep empty examples. Negative cases prevent a guessing prompt from looking artificially strong.

4. Optimize on one split, judge on another. Prompt search sees the optimization split. The gain only counts on the held-out split; otherwise you are measuring how well the optimizer memorized the benchmark.

5. A result belongs to one model-plus-examples pair. A score measured on Model A is not evidence about Model B. The application marks assumptions as prior only and actual runs as measured. Use Evaluation → Test lab → Models to measure transfer instead of assuming it.

From a number to a release

A benchmark result is evidence about one exact prompt. Every run stores a fingerprint of the text it measured. Production → Ship checks that fingerprint against the prompt being frozen, and writes the answer into the exported manifest:

  • measured — The prompt being released exactly matches the prompt in the cited run.
  • indirect — The cited run measured something related (e.g. the optimization pass), but not the exact release text.
  • unverified — No matching measurement is attached.

All three can be registered, but only a genuinely measured release can pass automatic approval. Approval is also gated by thresholds in prompt-playoff.yaml — the same thresholds CI enforces, with zero extra model calls required during approval.

Optimization

Prompt Playoff exposes four search strategies. Anything not installed is shown greyed out rather than disappearing, keeping the conceptual options clear.

nativeGreedy prompt rewrite loop: the built-in model critiques the prompt and rewrites it; rewrites that break input placeholders are discarded early. Needs no extra tools.
DSPy MIPROv2Joint Bayesian search over instructions and demonstrations together. In our benchmark, this optimizer produced the primary gains.
DSPy GEPAMaintains a population of prompt variants and evolves them.
DSPy BootstrapFewShotLeaves the instruction alone and searches for optimal demonstration sets.

Whatever wins remains text until you choose to adopt it: Adopt optimized prompt moves the winner back into your prompt workspace, or you can export it as a standalone technique runnable by ID.

Your own data matters more than the bundled data

The bundled datasets help you understand the tool. They do not prove anything about your production task — conclusions about your task must come from your data. Upload a .jsonl file directly:

{"id":"1","input":"Mara entered Veyr with Captain Orin.","expected":{"people":["Mara","Captain Orin"],"places":["Veyr"]}}

Only id and input are required. When expected is present, graders are inferred from its shape or can be supplied explicitly. For extraction: the gold answer should appear in the source text word-for-word, and keep rows where the correct answer is empty.

If you have no dataset yet

Datasets → Add dataset → Generate can generate candidate rows along a fixed taxonomy of failure modes (typos, irrelevant debris around input, reordered fields, missing data, conflicting instructions, injection attempts, filler). Deterministic checks run first to reject duplicates or broken rows before human review. Generated rows do not become ground truth until approved.

Build from what the model got wrong

Once you have a benchmark run, the most useful new examples are usually not random difficult examples: they are mutations around the failures your current prompt actually made. The dataset builder can seed from missed rows, keeping the original failure and mutating around it to target unresolved edge cases.

Model-generated seed inputs from multiple viewpoints can broaden vocabulary. When expected answers are generated, agreement across samples is recorded — low-agreement rows move to the front of the human review queue as a prioritization signal.

What Prompt Playoff cannot tell you

  • Turn a model judge's opinion directly into a release decision without human confirmation.
  • Make a tiny dataset statistically meaningful (six examples is not a measurement).
  • Verify vendor business performance claims printed on catalogue cards.
  • Reduce open-ended writing quality to a single objective number without human review.
  • Observe live production traffic.
  • Call arbitrary tools that have not been registered in the environment.
  • Export every stage of a multi-stage method to promptfoo (first stage only).
  • Assume a result transfers to another model without measuring in Test lab → Models.
  • Decide whether your benchmark examples truly resemble your production users (input drift measures difference, but relevance remains human judgement).

The principle behind the product

The product starts from a practical constraint: Before changing the model, find out how far the current one can actually go.

A surprising amount of model capability is hidden behind task formulation, examples, output contracts, retrieval context, and search strategy. Prompt Playoff exists to measure that headroom rather than assume it. For local and smaller models, this matters even more: the question is not simply whether a larger model scores higher, but whether the current model can meet required quality, reliability, latency, and cost once the prompt has been properly optimized.

Prompt Playoff is not built on the idea that prompts can be ranked once and for all. It is built on the opposite idea: Prompt performance is conditional.

Task + Dataset + Model + Prompt + Grader + Run Settings = Result

Change one of them and you may have changed the answer. That is why the product does not ask: “Which prompting technique is best?”

It asks: “Which technique is best here — for this task, on this model, against these examples — and is the difference large enough to believe?”

That is what the measurement is for.
