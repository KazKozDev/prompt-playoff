Evaluation guide

Where the numbers come from — the examples, the graders, the run — and when a result is not worth believing.

Русский

What a measurement here is

It is an exam for a prompt.

Take a pile of tasks whose correct answers are known. Run your prompt on a live model across all of them. Compare what the model said against the correct answer, and count the hits. Out comes a number.

The point is to replace "I think the prompt is better this way" with "0.83 against 0.71 on two hundred examples".

The three parts of the exam

The examples

The tasks themselves and their correct answers. One task per line of a file. They decide what the number is about.

The graders

Small pieces of code that compare the model's answer to the correct one and score it from 0 to 1. Each task type has its own — arithmetic and translation cannot be checked the same way.

The run

Which model, how many runs per example, which settings. This is what decides whether the number is repeatable or accidental.

What the public corpora are

A public corpus is a set of tasks that somebody else's research group collected and annotated, then released openly. The value is that nobody here tuned the data to produce a convenient result.

How the import keeps the data honest

  • The gold answer is sliced out of the finished sentence. Otherwise the name in the answer and the name in the text could differ by a space, and the model would be marked wrong for somebody else's spacing.
  • An entity type the schema does not ask for becomes an empty example, not a wrong one. If the only name in a sentence is a film title while the schema asks for people and places, the correct answer is empty rather than a penalty.
  • A share of empty examples is kept on purpose. Drop every case where there is nothing to answer, and a prompt that simply guesses starts looking excellent: its extra answers have nowhere to show up.
  • Corpus limitations are recorded, not hidden. In Few-NERD, for instance, two adjacent entities of the same type merge into one — that is the corpus's own property, and it is stated in the preset's notes.

How an answer gets checked

A grader takes the model's answer and the correct one and returns a number from 0 to 1. They come in two families, and both appear in the Graders table under every measurement.

Meaning — is the answer right

field_f1Partial credit over a list. Three entities out of four is roughly 0.86, not zero. Extras that were not in the gold answer are penalised too. This is the headline score for extraction.
exact_matchDid the whole thing match, with no leniency. Almost always far below field_f1, which is normal.
label_accuracyWas the category right. For classification.
numeric_closeDid the number match. Formatting is ignored — only the value counts.
unit_testsThe code from the answer is actually run against the task's own tests. The score is the share that pass. Execution happens in a sandbox with a restricted set of modules.
glossary_consistencyThe share of required terms translated the way the glossary demanded.
grounding_overlapHow much of the answer's wording actually occurs in the supplied sources. A blunt but working check against invention.
contains_allDid every required fact make it into the answer.
coverageRecall only: how much of what was wanted showed up. Extras are not penalised.
tool_successDid every tool call return a result rather than an error.
agreementHow much several answers agree with each other, when the method generates a batch.

Form — is the answer shaped right

json_validityDid the answer parse as JSON.
json_schemaDid it match the schema completely.
schema_shapeThe share of required fields that are present. Partial credit on form.
no_proseIs there chatter wrapped around the answer.
allowed_labelsIs the label from the allowed list rather than invented.
length_limitDid the answer fit the character limit.
omission_checkIs the answer truncated or bloated — its length is compared against the source.
deduplicationAre there repeats inside the lists.
python_syntaxDoes the code the model produced parse.
regex_matchDid the answer match the required pattern.

Graders are deterministic by default. The same answer always gets the same score, checking costs nothing and takes no time, and you can read the rule yourself.

For open-ended prose, where no rule fits, use Check → Pairwise judging: two answers, one rubric, and the order hidden from the judge. Every verdict lands in Production → Reviews and waits for a person. A model's opinion is never silently promoted to a measured result.

How the graders become the two headline numbers

quality is one chosen meaning-grader, whichever fits the task: field_f1 for extraction, label_accuracy for classification, numeric_close for arithmetic, unit_tests for code. In the Graders table it is marked headline; the others are shown beside it for reference.

reliability is the share of correctly shaped answers multiplied by stability — whether the model gives the same answer to the same input.

What to do with those two numbers is on the Help page.

Five rules, without which the number means nothing

1. A hundred examples, minimum. On six examples, a 5% difference is one example moving. On forty examples the threshold below which a difference is indistinguishable from noise is roughly 0.04. Anything smaller is not a result — Check → Significance will say so.

2. Three runs per example. With a single pass, stability is 1.000 by definition — not because it is stable, but because there is nothing to compare against.

3. Empty examples are mandatory. Cases where the right answer is "nothing" keep a prompt honest. Without them, the guesser wins.

4. For optimization, read the held-out split only. The search fits itself to the examples it saw. The gain only counts on the part it never saw.

5. A number belongs to one model-plus-examples pair. Carry it to another model and it is a guess again. The app says measured where it measured and prior only where it is assuming; Check → Model matrix is how the transfer gets measured instead of assumed.

The four searches behind Optimization

Chosen in the How to search field. Anything not installed is shown greyed rather than hidden, so the list is the same list every time.

nativeThe built-in greedy loop: the model critiques its own prompt and rewrites it, and the best variant survives. Nothing to install.
DSPy MIPROv2Bayesian search: it proposes instructions and example sets together, and learns from the scores they got. In our measurements this is the only one that produced a gain.
DSPy GEPAEvolution: keeps a set of variants nothing has beaten outright and breeds from those.
DSPy BootstrapFewShotLeaves the instruction alone and only picks the worked examples that go into the prompt.

What has already been measured

The finished reports live in docs/benchmarks/. In short:

  • Thirteen methods from the literature, on few-nerd: eleven out of twelve lost to the plain baseline prompt. The ranking tracked token spend almost exactly, in the wrong direction: the more a method "reasons", the worse it reads. Entity extraction is reading, not reasoning, and an intermediate restatement pulls the model away from the original text.
  • The built-in search against MIPROv2 on entity-extraction-hard, same split for both: the greedy loop delivered exactly +0.000, MIPROv2 delivered +0.090 while using half as many model calls.
  • A large cloud model behaved the same way on reading: a separate reasoning stage cost 0.028 quality at 2.9× the tokens and 4.4× the time. On arithmetic both methods hit the 1.000 ceiling, where no difference can show.

This is also why the catalogue is a catalogue and not a ranking: of the sixty-one methods on Reference → Techniques, which one wins is a property of your task, your model and your examples. That is what the measurement is for.

Your own data

The bundled sets are for finding your way around. Conclusions about your task can only come from your data. A .jsonl file, one task per line, uploaded straight from the interface:

{"id": "1", "input": "Mara entered Veyr with Captain Orin.",
 "expected": {"people": ["Mara", "Captain Orin"], "places": ["Veyr"]}}

Only id and input are required. Graders are picked from the shape of the expected answer; you can name them yourself in a graders field.

The one rule. The correct answer has to appear in the text word for word. If the text says "Captain Orin" and your gold says "Orin, captain", the model is marked wrong for not guessing your way of writing it. And keep the examples where the right answer is empty.

If you have no examples at all, Datasets → Build datasets generates rows along every axis of a fixed taxonomy — a typo, debris around the input, reordered fields, missing data, an instruction that argues with the prompt, an injection attempt, an answer buried in filler — and shows you which axes are still empty. Deterministic rules object first: a row that duplicates another, or carries an answer copied from an input that has since lost half its content, is flagged before anyone reads it. Nothing generated becomes truth before you approve it.

Once a run exists, the useful rows are no longer the awkward ones in general. Building from what it got wrong seeds a new set from the examples the last benchmark did not score full marks on, keeps each one unchanged, and mutates around it — so the next set is aimed at the part of the task this prompt is actually failing, rather than at more of what it already handles.

A model can write the seed inputs too. Drawing several samples instead of one and pooling them widens the vocabulary; asking each sample to write as a different reader of the task widens it further. If you also ask for a proposed answer per row, it is sampled several times and the row keeps the answer the samples agreed on — with the level of agreement recorded, so the review queue opens on the rows the generator could not settle with itself. None of that is a quality score. It only decides what a person looks at first.

What this cannot do

  • Turn a model's verdict into a release decision without a person approving it.
  • Say anything meaningful on a tiny set. Six examples is not a measurement.
  • Call arbitrary tools in agent tasks: only registered ones work, and a calculator is what ships.
  • Export a multi-stage method to promptfoo — only the first stage goes out.
  • Assume a result carries to another model; that is what Model matrix is for.
  • Tell you your examples resemble production. Production → Monitoring watches for the drift, but the resemblance is your judgement.
