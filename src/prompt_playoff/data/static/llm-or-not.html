Do you need an LLM at all?

Everything else in this workspace assumes the answer is yes. This guide is the question before it: which of eight solution classes the task actually needs, and what it costs to pick one too high.

What this decides

A prompt that scores 0.91 on a task that a lookup table solves exactly is not a good result. It is a slower, less reliable, more expensive way to be right slightly less often, and no measurement taken inside this tool will ever say so, because the tool starts after the choice has been made.

So make the choice deliberately. The rule is one line: pick the lowest class that solves the task, not the highest class that could. The classes are a ladder, each rung strictly more capable and strictly more expensive to build, run and keep working.

This guide is the sibling of Prompt vs Fine-Tuning. That one answers "the prompt is not enough — now what"; this one answers "is a prompt more than enough".

The ladder

Walk the checks in order. Stop at the first that applies, and take that rung. Do not look further down the list for something that would also work — everything below the stop is something that would also work, and that is exactly the trap.

ClassStop here when
0 — Script / rulesAn explicit rule does it: a regular expression, a lookup table, a SQL query, an if
1 — Classic MLThere is labelled history, the schema is stable, and the volume is high
2 — Single LLM callNo knowledge from outside the model is needed
3 — LLM + retrievalPrivate or live knowledge is needed, and one retrieval step answers it
4 — Fixed pipelineThe steps are known before the run and do not change with the input
5 — Single agentThere are external actions, and the next step is decided at runtime
6 — Multi-agentParallel independent inputs, mandatory context isolation, or different tool permissions per role
7 — Human onlyThere is no verifiable ground truth and the cost of an error is high
Class 7 is a real answer, not a failure. A task with nothing to check an answer against and a serious penalty for a wrong one has no measurement that would tell you the system is working, which means it has no way to stop being wrong.

Establish the features first

The checks above read features of the task, so settle those before walking the ladder. Each is a property of the work, answerable without knowing what you intend to build.

FeatureValuesWhat it decides
Input structurestructured · semi-structured · free text · multimodal · conversationWhether a rule can parse it at all
Output spaceclosed label · schema · open text · action · rankingClosed spaces are where classes 0 and 1 live
Knowledge sourcenone · private docs · live systems · public web · labelled historyThe boundary between class 2 and class 3
Path knownyes · no · partlyThe boundary between class 4 and class 5
Side effectsnone · read · write · irreversibleWrites and irreversible actions are what makes an agent expensive
Volumelow · medium · highHigh volume repays training a model; low volume does not
Latency budgetseconds · minutes · overnight batchA batch window makes several classes affordable that a live one does not
Error costlow · medium · high · regulatedRegulated pushes towards a person in the loop regardless of the rung
Ground truthavailable · proxy · noneNo ground truth means no score, and no score means class 7

The last one is where this tool connects. Every number the workspace produces is computed against examples whose answers are known. If the task has no ground truth and no usable proxy, there is nothing here for the tool to measure, and that is worth finding out before writing the prompt rather than after.

Pipeline or agent

This is the boundary that is misdrawn most often, in both directions, and almost always in public write-ups that have something to sell.

If the sequence of steps can be drawn before the run, it is a fixed pipeline — class 4 — even when it contains five model calls, a retrieval step and a formatter.

An agent is not "a system with several LLM calls in it". An agent is a system where the next step is not known until the previous one returns. Transcript → summary → action items → draft email → CRM record is five steps in one order every time; nothing decides anything. It is a pipeline, and it should be built as one, because a pipeline can be tested step by step, retried at the step that failed, and reasoned about when it breaks at three in the morning.

The cost of getting this wrong is not the model bill. It is that an agent's control flow is decided by a model, so a pipeline dressed as an agent has replaced a for loop you can read with one you have to evaluate.

Agent or multi-agent

Class 6 requires one of exactly three conditions. Decomposition on its own is not one of them.

  • Parallel independent inputs. Twenty documents that do not need to know about each other, processed at once.
  • Mandatory context isolation. One role must not see what another role saw — a reviewer that must not be shown the author's reasoning, a grader that must not know which answer is the incumbent.
  • Different tool permissions per role. One part may write to the CRM and another may only read, and the boundary has to be enforced somewhere other than in the instructions.

Splitting one job into "a researcher, a writer and an editor" that run in a fixed order and share everything is class 4 with the steps given names. It costs more, fails in more places, and the hand-off order was fixed the whole time.

Name what it did not need

Once you have a class, write down two things and keep them next to the system.

The heavier thing you nearly built. Name it concretely: "an agent with write access to the CRM", "a multi-agent review board", not "something more complicated". If the honest answer is that the task genuinely sits at the top of what it needs, write that instead.

Why it would not have paid. Ground this in the features, not in taste: the path was known, the output space was closed, the error cost was low, there were four actions and they were all reads. A generic sentence here is the same as no sentence.

These two lines are what makes the decision reviewable a year later, when the person asking why it is "only" a pipeline is not you.

Six tasks and where they land

Deployments that have been described publicly, read against the ladder. Every figure below is what the company or its vendor published about itself; none of it has been verified here, and a result without a stated baseline is a number without a claim in it.

TaskClassWhy not a rung higher
Route a support email by domain and tag0The rule is expressible. A model adds a probability of being wrong to a task that currently has none
Score a card transaction for fraud1Labelled history, a stable schema, and volume that no per-call model price survives
An internal assistant for drafting and rewriting2There is no workflow. It is an interface to a model, and calling it a pipeline would not add a step
Answer questions from internal HR policy3Retrieval and synthesis, no action taken in any system. An agent would be given tools it never calls
Meeting transcript to summary, action items and a CRM record4The five steps are the same five steps every time. Nothing is decided at runtime
Second-line support: delivery status, refunds, address changes5Genuinely dynamic — when to call tracking, when to ask the customer, when to refund — but one conversation with no independent workstreams, so not class 6

The pattern in the last column is worth more than the rows. In five of six, the reason the heavier class was wrong is one feature: the path was known, the output space was closed, or nothing was written anywhere.

Where this leaves the rest of the workspace

The class you land on says what this tool can do for you.

ClassWhat to do here
0 — 1Nothing. There is no prompt to optimise. Close this and write the rule
2 — 4This is what the workspace is for. One prompt per model call, measured against examples, gated in your repository
5 — 6The agent's control flow is not measured here, but every prompt inside it is. Measure them one at a time; Spot checks will tell you whether the tools were called as intended
7There is no score to produce. What a model can do is prepare material for the person who decides

Class 3 and above always contain at least one class 2 problem inside them: a single call, with a prompt, that either does its job or does not. That call is what this workspace measures, and improving it does not require agreeing about the architecture around it.

The catalogue behind this

The ladder and the two boundary tests come from a separate catalogue of recorded deployments, kept outside this repository because it changes on its own schedule and carries obligations this tool does not: every row cites a source and an evidence tier, results are self-reported until shown otherwise, and rows that cite nothing are counted rather than hidden.

That separation is deliberate. A guide is stable and can ship inside a versioned tool; a catalogue of what companies published last quarter cannot, and a stale row served from inside an application reads as the application's own claim.
