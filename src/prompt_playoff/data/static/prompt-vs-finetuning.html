When to fine-tune a model — and when prompting is enough

A practical, research-backed guide to choosing between prompt engineering, few-shot in-context learning, RAG, fine-tuning, distillation, and tools/agents — based on quality, cost, latency, and production stability.

Fine-tuning is not for when you simply want to “make the model smarter.” It becomes justified when evals show that the behavior you need cannot be achieved reliably, cheaply, or quickly enough with prompting, in-context examples, retrieval, or a more capable base model.

1. Start by identifying the type of problem

Prompting, retrieval, fine-tuning, and tool use solve different problems. Large language models can often adapt to a task from instructions and demonstrations without any weight updates, which is why prompting and in-context learning should be treated as genuine adaptation mechanisms rather than merely a UI layer. [1]

ProblemBest first approach
The model does not understand what exactly you wantPrompt engineering
You need to demonstrate the desired behavior with examplesFew-shot / ICL
The model lacks relevant facts or documentsRAG
The information changes frequentlySearch / RAG / tools
The model must call APIs, databases, CRM systems, or softwareTools / agent
The task is understood, but the required behavior remains inconsistentFine-tuning
A large repeated prompt dominates inference costFine-tuning / distillation
A smaller model needs to specialize in a narrow, repetitive taskFine-tuning
Instruction tuning research shows that supervised training on instruction–response pairs can materially change how reliably a model follows instructions and generalizes to unseen tasks. [2] A recent survey similarly characterizes instruction tuning as a mechanism for improving model controllability and task alignment. [7]

3. When prompting is usually enough

Consider a standard extraction task:

“Extract the customer name, order ID,
and issue from this email. Return JSON.”

A capable language model already has general text-understanding and extraction abilities. Few-shot prompting lets it infer task structure from demonstrations without gradient updates. [1]

Extract:
- customer_name
- order_id
- issue

Return valid JSON using this schema...
Rule: if the capability already exists, first try to expose and constrain that capability through instructions, output schemas, examples, and evaluation.

4. A strong case for fine-tuning

Suppose a company has 73 internal support categories whose boundaries depend on organization-specific rules:

"refund pending" → PAY_REFUND_PENDING

if refund initiated less than 3 days ago →
PAY_REFUND_PROCESSING

but if merchant disputed →
MERCHANT_DISPUTE_REFUND

except enterprise users →
ENT_REFUND_ESCALATION

If you also have 20,000 correctly labeled historical tickets, you now have a classic supervised adaptation problem: a stable input distribution, a stable target taxonomy, and many examples of desired behavior. Research on instruction tuning demonstrates that supervised examples can teach response conventions and task-following behavior. [2] [4]

After fine-tuning:

The potential gain is not only quality. A successful tuned model may reduce repeated prompt tokens, decrease latency, improve consistency, and make it possible to deploy a smaller model.

Fine-tuning is usually not the first mechanism to choose when the main requirement is access to a large, changing body of facts. Retrieval-Augmented Generation was specifically introduced to combine parametric model knowledge with an external non-parametric memory, addressing problems such as provenance and updating world knowledge. [3]

Knowledge → context.

But domain fine-tuning can still help

Fine-tuning can adapt terminology, response conventions, classification boundaries, and specialized task behavior. The LIMA results are a useful reminder that a relatively small quantity of carefully curated examples can teach strong response behavior even when most factual knowledge comes from pretraining. [4]

             DOMAIN BEHAVIOR
                    ↓
              Fine-tuned LLM
                    ↑
                    │
User → Retrieval → Context

Therefore, RAG and fine-tuning are complementary: retrieval can supply current knowledge while tuning shapes how the model behaves with that knowledge.

1. You have many examples of “this is correct”

INPUT → CORRECT OUTPUT
INPUT → CORRECT OUTPUT

This is especially attractive when the target behavior is easier to demonstrate than to describe as a long list of rules. Research such as LIMA shows that carefully curated supervised examples can exert substantial control over model behavior. [4]

Long-context ICL can remain effective even with hundreds or thousands of demonstrations, but those demonstrations must be processed at inference time. This creates a real tradeoff between context-based adaptation and weight-based adaptation. [5]

These are often narrow tasks with measurable labels and clear error rates — exactly the environment where supervised adaptation can be evaluated objectively.

EMNLP 2025 experiments across eight text-classification tasks found that specialized smaller models often needed only a small number of labeled samples — around 100 on average in the tested setting — to reach or exceed the performance of larger general models. The exact break-even point varied substantially by task. [6]

7. When fine-tuning is probably the wrong move

  • A prompt produced one bad answer.
  • You mainly need fresh or frequently changing facts.
  • You have only a handful of weak or contradictory examples.
  • The task definition changes every week.
  • The taxonomy itself is still unstable.
  • You have no representative eval set.
  • You cannot describe the failure modes you expect tuning to fix.
  • The base model fundamentally lacks the capability required by the task.
incapable base model
+
500 examples
≠
frontier reasoning model
Fine-tuning is usually strongest as specialization. It should not be treated as a magical way to manufacture arbitrary new capabilities from an unsuitable base model.

8. Long-context models changed the boundary

The old heuristic “a few examples means prompting; many examples means fine-tuning” is no longer sufficient. NAACL 2025 experiments found that long-context ICL can continue improving with thousands of demonstrations on some tasks. The same study found that fine-tuning was more data-hungry in the tested settings, but could exceed long-context ICL with additional training data. [5]

Today you should consider all of these:

quality
inference cost
training cost
latency
context size
dataset quality
task stability
traffic volume
maintenance burden

This makes the decision economic as well as statistical: the same target accuracy can have very different operational costs depending on whether adaptation lives in the prompt or in the weights.

Fine-tuning can therefore be justified even when prompting already reaches the quality target: the optimization objective may be inference economics rather than raw accuracy.

10. The decision criterion

Quality Gain + Inference Savings + Latency Gain
>
Training Cost + Data Cost + Maintenance Cost

The task should also be stable enough that the learned specialization will remain useful long enough to repay the cost of dataset creation, training, evaluation, and maintenance.

The useful question is not “Can this be solved with a prompt?”
It is “Can prompting meet the required quality, cost, and latency SLO on the real data distribution?”
If the bottleneck is…Use
Task specificationPrompt
Missing demonstrationsFew-shot / ICL
Missing or fresh knowledgeRAG / Search
External actionsTools / Agent
Stable, task-specific behaviorFine-tuning
Excessive inference cost or latencyFine-tuning / Distillation
Prompting tells the model what to do in this context.
RAG tells it what it needs to know in this context.
Fine-tuning changes what it tends to do by default.

For smaller local models, specialization can become attractive relatively early. Recent controlled experiments show that small fine-tuned models can reach or outperform larger general-purpose models on narrow classification tasks with surprisingly modest amounts of labeled data, although the break-even point is strongly task-dependent. [6]
