How the workspace writes, measures, and ships a prompt

What the workspace does, in the order you meet it, and how to read every number it gives back.

What this is for

The usual way to write a prompt is to guess, change it until it feels better, and ship the feeling. There is nothing to check the feeling against.

Here you describe the task in your own words. A method with a track record is picked for it, the finished prompt is written out, and that exact text is run on a real model across examples whose answers are known. What comes back is two numbers and a record of how they were produced. Everything runs on your machine.

If you do only one thing

Smart run sits at the top of the rail and on the home screen. It writes the prompt, measures it on your examples, improves it over a few rounds, and stops at the first step that needs a decision from you. Minutes, not seconds.

Everything below is that same path with the steps pulled apart, for when you want to see one of them or change it.

Five sections

The rail has five, and they are the life of a prompt in order. Each opens to name its screens; the home screen shows the same five as tiles, each carrying the one fact that decides whether you need to go there. Below them, in the rail's foot, sit the two screens that belong to no stage: Models & keys and Jobs & logs.

Prompt Studio

The prompt itself, the three measurements taken on it as it stands — one run over your examples, the techniques that were in the running scored side by side, and the search for a better wording — and the catalogue of sixty-one techniques it was written from.

Datasets

The rows every score is computed against. Bring your own, import a public set, or generate them here — and the library opens on a shelf of twelve categories of business work, fifty-nine tasks between them, each task mapped to the set closest to its shape. A number only means something when these look like your real inputs.

Evaluation

Everything that compares across — runs, models, contexts, two answers — and everything that questions the numbers themselves.

Production

The gate between a prompt that scores well here and a prompt running in front of real users: spot checks, reviews, regressions, and releases.

Docs

The catalogue of techniques and the three guides — this one, the evaluation contract, and prompting versus fine-tuning. Nothing here changes your prompt.

Three models, three jobs

The workspace uses three, and confusing them explains most surprises. Models & keys — in the corner of the rail, and behind the model chip in the bar at the top — is where all three are set.

The prompt engine

Writes the finished prompt from your description, and writes the rows the dataset builder generates. It never produces a score.

The evaluation model

Runs the prompt on your examples. Every number you see anywhere in the app came out of this one.

The judge

Marks answers against each other in pairwise judging. Leave it blank and the prompt engine stands in — never the evaluation model, which would be marking its own paper.

Until an evaluation model is set, every screen that would run something says so and links to the one place that fixes it. The chip in the bar shows which model is answering for the numbers on screen, and switches it without leaving the screen.

The path, step by step

1. Describe the task

In the left column, in plain words: what the model should do, what comes out, and the constraints that matter. Choose whether you want a prompt ready for this one task or a reusable template with a placeholder, then press Create my prompt.

2. Read what was written

Prompt Studio → Prompt text shows the finished text — exactly what will be sent to the model — with the ranked techniques and the reason each was suggested beside it. Any of them can be compiled instead.

3. Choose the examples

Datasets. Twenty-three sets ship with the app: eleven task benchmarks, and twelve covering work businesses pay a model to do — email, meetings, support, contracts, finance, marketing. Five more business sets remain visible as source-only because their upstream terms do not permit redistribution. In Add dataset, upload your JSONL, import public rows, or use Generate when you have none. This is the choice that decides whether the number means anything.

4. Measure

Prompt Studio → Measurement. Set what to measure against and how many runs per example, then Measure now. This is the step that turns an opinion into a number.

5. Compare the techniques

Prompt Studio → Technique comparison scores every recommended technique on the same examples, so the ranking is measured rather than assumed.

6. Push further

Prompt Studio → Optimization rewrites the prompt over several rounds, scores every version, and keeps the best. Read the held-out numbers only — see below. A winner stays on that screen until Adopt optimized prompt puts it on Prompt text.

7. Question the result

Results → Significance puts an interval around the difference. Test lab → Models and Test lab → Context ask whether it survives a different model or a different amount of context.

8. Ship it

Production → Ship freezes the prompt against the run that measured it, and Export writes two files for your repository: the manifest, carrying the exact text, its fingerprint and the run behind it, and a checks: block for prompt-playoff.yaml. From there prompt-playoff check enforces it in CI, which is where a gate actually guards something. A release advances only on a run that measured this exact text, against those same bars.

The two numbers that matter

quality — how correct the answers are
below 0.5 — bad
0.5–0.8 — passable
above 0.8 — good

It gives partial credit. If the model found three of the four things it should have, that is roughly 0.85, not zero. So 0.78 means "mostly copes, but regularly drops one".

reliability — whether the answer is shaped correctly

This is about form, not meaning: the answer came back the way it should — valid JSON, all required fields, nothing extra wrapped around it — and it came back the same way each time.

Do not confuse the two. You will see reliability 1.00 next to quality 0.4. That means the model is neatly and correctly formatting the wrong answers.

The other numbers

mean latencySeconds spent on one example.
mean tokensTokens spent on one example. That is money, if the model is paid.
mean callsHow many times the model is called per example. More calls means slower and pricier.
failuresExamples that did not run at all. Should be 0.
stabilityWhether the model gives the same answer to the same question.

What to do about what you see

What you seeWhat to do
Low quality, high reliabilityThe shape is fine, the meaning is not. Look at Where it went wrong under the measurement — the three worst cases, with what the model actually answered. Low quality usually hides one repeated mistake.
Low reliabilityThe model is padding the answer with chatter. Tick Structured output in Models & keys — then the format is enforced by the runtime instead of politely requested.
failures above zeroThe model is too slow to answer in time. Use a faster one — a thinking model can spend forty seconds on one example.
Good but expensiveCompare against a simpler method. Three model calls often do not pay for themselves in quality.
Numbers jump between runsToo few examples, or one run per example. Raise both.
Good here, wrong in productionYour examples do not look like your real inputs. Ship → Spot checks measures exactly that gap: paste the inputs you have seen since against the ones you tested on.

Optimization, and the one table to read

Optimization rewrites the prompt itself and checks whether that helped. It splits your examples: most are used for the search, and a held-out part is kept back, unseen.

Look only at the Held-out validation table. If it shows zeros or a minus, nothing improved, whatever the table above it says.

This happens often. The search easily fits itself to the examples it trained on and does no better on new ones. That is normal — just do not trust the numbers from the upper table.

Four ways to get burned

1. One run per example measures nothing about stability. At Runs per example = 1, stability always reads 1.000. That does not mean "stable", it means "nobody checked". Set it to 3. The model can answer differently every time and you would never see it.

2. Few examples, worthless numbers. On six examples a 5% difference is one example moving. Use a hundred or more if you intend to decide anything from the result.

3. A number belongs to one model. Measure on one model and it is a guess again for another. The app says measured where it measured and prior only where it is assuming. Evaluation → Test lab → Models is how you find wording that only works on the model you wrote it for.

4. A model's verdict is not truth. Answer judging uses a model to read two answers pairwise and blind. Every verdict goes to Reviews and waits for a person; nothing is promoted to a benchmark result on a model's say-so.

Your own examples

The bundled sets are for finding your way around. Draw conclusions from your own. A .jsonl file, one task per line, uploaded straight from Datasets → Add dataset → Upload file:

{"id": "1", "input": "Mara entered Veyr with Captain Orin.",
 "expected": {"people": ["Mara", "Captain Orin"], "places": ["Veyr"]}}

Only id and input are required. The rest is worked out for you.

One rule. The correct answer has to appear in the text word for word. If the text says "Captain Orin" and your answer says "Orin, captain", the model is marked wrong for not guessing your way of writing it.

And keep the examples where the right answer is empty. Without them, a prompt that simply guesses looks excellent: its invented answers have nowhere to show up.

Details — if you need to dig deeper

Where quality comes from

For extraction it is the field_f1 grader: it counts both what the model missed and what it invented. In the Graders table it is marked headline. Next to it sits exact_match — did everything match outright, with no allowances. It is almost always far lower, and that is expected.

For prose — a reply, a subject line, minutes — it is token_f1, word overlap with the one answer the set records. Read it as a rough check, and settle wording with Evaluation → Answer judging.

The format checks live there too: json_validity (did it parse), json_schema (did it match the schema fully), no_prose (no chatter around it). If json_validity is 1.00 while field_f1 is low, the problem is comprehension, not format.

Where reliability comes from

It is the share of correctly formatted answers multiplied by stability. Hence the catch with runs per example: on a single run stability is 1 by definition, so reliability looks inflated.

p95 latency

The time 95% of examples fit inside. If it is far above the mean, there are occasional very slow answers. For interactive use that matters more than the mean.

Measured versus declared

Declared is the estimate written into the method's own config before anything was measured. Measured is what actually happened on your model and your examples. A gap between them is the point, not a mistake — once measured, the config stops being used.

Comparing methods

The Weighted column is the combined score under your weights. But if token cost carries any weight, a method can win by being cheap while being worse at the job. Check the quality column too.

The latency and token columns in a comparison are relative — computed against the best method in that same run, so they do not transfer to other runs.

Pareto front in optimization

The variants that nothing beat on every measure at once. One of them is sometimes both more accurate and cheaper than the declared winner.

Prompt stages

Some methods split the prompt into several stages, which means several model calls in a row. Labels like {previous} mark where the previous stage's output gets inserted at run time.

Where the runs are recorded

Evaluation → Results keeps every run this server has made, newest first, with a version-to-version diff and a CSV export. Aggregate numbers only: prompts and raw model answers are not stored there. Jobs & logs shows what is running right now and what every finished run did.
